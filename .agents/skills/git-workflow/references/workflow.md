# Git 工作流与工作模式

## 选择模式

这是模板工作约定，不是宿主权限配置；字段不能授予凭证、绕过仓库保护或扩大用户授权。project 模板以 project.json.git 为单一配置源；独立 wiki 使用 git-policy.json。缺失配置时读取目标仓库 AGENTS.md 和当前用户指令，不推断可推送或合并；只有用户明确指定或仓库既有约定才选择写入模式。检查脚本仅报告现场，不执行交付。

| delivery | 文件与提交 | 远端交付 | 完成条件 |
| --- | --- | --- | --- |
| read-only | 读取与检查，不改文件、不提交 | 不 fetch/push/PR | 报告证据及限制 |
| local | 在任务范围修改、验证、精确提交 | 不推送、不建 PR | 本地提交及验证结果 |
| direct | 在获授权且允许直推的目标分支修改、验证、提交 | 普通 push，不绕过保护 | 远端 SHA 与本地一致 |
| review | 从核验后的 base 建任务分支，修改、验证、提交 | push 并创建或复用 PR | 当前 head 的 CI、Review、冲突状态已核对；保持 PR open |

默认 review；auto_merge 固定 false。local/direct/review 各步骤仍受当前用户限制和实际工具权限约束；例如明确不推送时本轮停在本地，不改共享配置。模式不是任务类型：文档、代码、知识更新均按目标仓库模式处理。只读审查请求不因仓库默认 review 而变成写入任务。

protected_branches 是 review 模式防止直接交付的提示清单，不代替平台保护。direct 只有目标仓库明确允许时才可直推；拒绝时转任务分支/PR 须符合当前请求，不能强推绕过。base 分支从已核验的远端默认分支或任务指定分支确定，不硬编码 main，也不修改远端默认分支。

## 开始与同步

1. 核对修改文件的真实 Git 根、当前分支、远端身份、默认分支、upstream、工作树、索引、未推送提交、冲突、进行中的 Git 操作和 worktree 占用。先执行 `node scripts/git-check.mjs`（若该目标仓库提供），再按实际工具补查远端状态。
2. 有既有修改时保留并识别归属；能分离则只做本任务，存在重叠先补齐事实。不自动 stash、reset、clean、覆盖、切走他人 worktree 或改写历史。
3. read-only 不执行同步；其他模式仅在任务允许网络同步时 fetch。工作树/索引干净、无未推送提交和 Git 操作时，可对核验后的目标执行 `git pull --ff-only`；分叉或保护失败保留现场，不自动 rebase。
4. review 模式从核验后的 base 建 `codex/<主题>` 分支。旧任务分支仅在确认属于同一任务时复用；不把其他任务的提交带入本次 PR。远端查询失败不猜 base、head 或创建重复 PR。

## 实现与提交

读取目标仓库规范与适用技能，按任务范围实现。选择该仓库的验证入口，记录基线失败与新失败的区别。代码检查、运行结果、报告持久化、消息交付和线上验收分别报告。

只暂存精确文件或 hunks；检查暂存 diff、未跟踪文件、gitlink、凭据、原始聊天、业务数据和生成产物。使用 Conventional Commits，说明变化及原因；真实无变化不创建空提交。提交失败先定位原因，不跳过 Hook 或改写既有提交。

## 推送、PR 与模式完成

- local：记录本地 SHA 后结束，不因存在 origin 自动 push。
- direct：先检查全部 outgoing 提交，确定均属于授权范围，再普通 push。推送拒绝或回执不明时先查远端 SHA，不创建重复提交或盲目重试。
- review：先查同仓同 head/base 的已有 PR，创建或复用；核对目标、base、当前 head SHA、真实 diff、CI、必需审批、Review 和可合并状态。未知不算通过。新提交使旧 head 的审核结果失效，必须重新核对。
- CI/Review 失败：修复本任务问题、重新验证并普通 push；无法处理的环境、权限或业务冲突保留分支与 PR 并说明。默认不无限重试，不绕过检查。
- 分支落后或冲突：仅在任务范围允许、工作区干净且可以保留双方有效改动时普通 merge base；不自动 rebase/force-push，不用整文件 ours/theirs 掩盖语义冲突。证据不足保留现场。
- 合并必须有针对当前 PR 的明确授权并复核当前 head/base 与全部门禁；模板不自动合并。PR 合并、发布 Release、部署、外部消息、删除分支/worktree 是不同动作，各按当前授权处理。确认远端提交安全后才清理本任务创建的临时 worktree，不删除用户工作区。

## 项目、业务仓库与 wiki

根项目、repositories 下业务仓库、独立 Git wiki 各自按真实 Git 根检查、验证、提交和交付，模式不自动继承。普通目录 wiki 随所属项目提交；独立 wiki 在其自身仓库交付；Git 子模块先交付子仓，再在当前任务明确包含版本指针更新时提交父仓 gitlink。

根仓仅同步自身时不递归初始化、切换或更新业务仓库/wiki。不因普通目录名或 project.json.repositories 列表就推断可下载、提交或推送。agent-repo 的同步仍以角色登记与 .gitmodules 的现有合同为准。

跨仓交付不是原子事务。逐仓记录：分支、提交、推送、PR、验证和剩余步骤；部分成功保留已完成结果，不用回滚或改写历史掩盖。知识归档、正文构建、CI、PR 合并与人工业务审核分别成立；自动检查不填写 verified 或自动改为 stable。

## 交付清单

说明本轮有效模式及依据、目标仓库/分支、变化、验证结果、本地 SHA、远端是否一致、PR 与当前 head 门禁、未完成项和下一步。不要将“已提交”写为“已推送”，或把 PR 创建写为已合并/已部署。
